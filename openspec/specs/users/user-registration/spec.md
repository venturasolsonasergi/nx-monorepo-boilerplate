# Spec: User Registration

## Purpose
Define the externally observable behavior for registering users through the users service.

## Requirements

### Requirement: Register a user with valid details
The users service SHALL accept a valid user registration and persist the user with an identifier generated by the database.

#### Scenario: Successful registration
- **WHEN** a client submits non-empty name, surname, email, address, and phone values to `POST /users`, with a valid email address
- **THEN** the service trims the string values, persists the user, and returns `201` with the persisted positive integer id and the normalized user fields

### Requirement: Reject invalid registration details
The users service SHALL reject a registration when a required field is missing or empty after trimming, the email format is invalid, or an unrecognized field is supplied.

#### Scenario: Required field is missing
- **WHEN** a client submits a registration without one or more required fields
- **THEN** the service returns `400` with a validation error describing each missing field

#### Scenario: Field value or request shape is invalid
- **WHEN** a client submits an empty required string, an invalid email, or an unrecognized property
- **THEN** the service returns `400` with validation details identifying the invalid field or property

### Requirement: Email addresses are unique
The users service SHALL prevent two persisted users from having the same email address.

#### Scenario: Email already exists
- **WHEN** a client submits a valid registration using an email that is already persisted
- **THEN** the service returns `409` with the conflict response and does not create a second user
